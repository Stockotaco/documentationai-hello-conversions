---
title: Meta Conversions API
description: Add a Meta Conversions API destination in Hello Conversions so CRM conversions — leads, purchases, pipeline stages — reach your Meta pixel server-side.
---

Anything that happens after the click — a form filled in your CRM, an opportunity moved to Won, an order paid days later — never reaches the browser pixel. A Meta Conversions API destination sends those events to your pixel from our servers instead.

<Callout kind="info">
  This is the Meta **destination** — conversions going out to your pixel. Pulling ad spend and creative performance *in* is a separate connection: see [Meta Ads as a source](/connect/sources/meta-ads).
</Callout>

## Before you start

Two things from [Meta Events Manager](https://business.facebook.com/events_manager2):

| What | Where to get it |
| --- | --- |
| **Pixel ID** | Events Manager, under Data Sources. A long numeric ID, e.g. `123456789012345`. |
| **Conversions API access token** | Events Manager → Settings → Conversions API → generate an access token. |

A token scoped only to sending events is enough — we never read pixel metadata.

<Callout kind="warning">
  Generate the token against the same pixel you enter as the Pixel ID. A token from a different pixel passes the connection test on the token but fails on the pixel, and Meta's error isn't always clear about which half is wrong.
</Callout>

## Add the destination

<Steps>
  <Step title="Open Destinations">
    **Settings → Integrations → Destinations** → **Add Destination**.
  </Step>
  <Step title="Choose Meta Conversions API">
    Pick it from the provider list.
  </Step>
  <Step title="Fill in the fields">
    | Field | Notes |
    | --- | --- |
    | **Name** | Your label, e.g. `Main Pixel`. Shown in the destinations list and the connection picker. |
    | **Pixel ID** | From Events Manager. Paste the number — no dashes or spaces. |
    | **Conversions API Access Token** | Masked in the form; the eye icon reveals it. |
    | **Website URL** | Fallback `event_source_url`, used when the event carries no page of its own. Worth setting — Meta expects a URL on every website event, and without one you lose attribution signal. |
    | **Health & Wellness Brand** | Attributes every conversion to the Website URL above, ignoring the page the event came from. Needs a Website URL to do anything. |
    | **Default Currency** | Currency for events that carry none — pipeline-stage conversions, for example. Sales that specify a currency in GHL keep theirs. |
  </Step>
  <Step title="Test the connection">
    **Test Connection** posts a sample `PageView` tagged with a generated test event code, so Meta treats it as a test rather than a live conversion. A pass reports how many events Meta accepted; a failure shows Meta's own error message.
  </Step>
  <Step title="Save">
    Click **Create**. The destination appears under **Active** once a test succeeds.
  </Step>
</Steps>

You can add several Meta destinations to one project, one per pixel, and route different events to each.

## Point events at it

A destination is the address, not the instruction. To start delivering, create a **connection** under **Settings → Workflows → Connections**: pick a source event type, pick this destination, and optionally set a custom event name and filters. See [Connections](/conversion-tracking/connections) for filters and routing, and [How delivery works](/conversion-tracking/how-delivery-works) for what happens in between.

The custom event name is what Meta receives as `event_name`. Use a standard Meta event where one applies — `Purchase`, `Lead`, `CompleteRegistration` — so Meta's optimization and reporting recognize it. Left blank, the source event type is sent as-is (`made_purchase`, `contact_created`), which Meta accepts as a custom event.

## What gets sent

Each delivery is one `POST` to Meta's Conversions API for the destination's pixel:

| Block | What it carries |
| --- | --- |
| **Identity (`user_data`)** | Email, phone, first name, last name, city, state, postal code and country, SHA-256 hashed before they leave our servers. Phone is normalized to digits first, with a `1` prefix on bare 10-digit US numbers. Contact ID is sent unhashed as `external_id`; IP address and user agent unhashed, as Meta expects. `fbc` and `fbp` ride along when we have them. How complete this block is drives [match quality](/conversion-tracking/match-quality). |
| **Event details** | Event name, event time, `action_source` (`website` by default), and `event_source_url` — the page the conversion happened on, taken from the contact's attribution (last touch first, then first touch), falling back to the destination's Website URL. With **Health & Wellness Brand** on, the Website URL is used for every event regardless of where it came from. |
| **Value (`custom_data`)** | `value` and `currency`, always. Non-monetary events get `value: 0` rather than nothing, because Meta's diagnostics flag events missing either field. Currency resolution: the event's own currency from GHL, then the destination's Default Currency, then USD. Meta converts to your ad account's currency itself. |
| **Order contents** | When the source event carries line items: `contents` with product ID, normalized title, item price and quantity, plus the order ID. Product names are lowercased with emoji and punctuation stripped. |

<Callout kind="note">
  An order with line items also produces one extra event per item, named `{EventName}_{product_name}` with that item's own value. This is deliberate — it lets you build product-level custom conversions in Meta — but it means the event count in Events Manager is higher than your order count. Your main `Purchase` event still carries the full order value.
</Callout>

## Deduplication

Every event carries an `event_id` of `hello-` plus the order ID (or the transaction ID for subscription rebills, since rebills reuse the original order's ID). Meta collapses events sharing the same `event_name` and `event_id`, so two connections firing for one sale count once.

<Callout kind="alert">
  This does **not** deduplicate against your browser pixel, which doesn't send our `hello-` prefixed IDs. If your funnel already fires a browser `Purchase` on the thank-you page and you also send `Purchase` from here, expect both to be counted. Either send a different event name server-side, or stop firing the browser event for that conversion.
</Callout>

## Confirm events are arriving

<Steps>
  <Step title="Check the destination status">
    On **Settings → Integrations → Destinations**, the destination should sit under **Active** with a green dot. **Error** puts the last failure message on the card — usually an expired or revoked token.
  </Step>
  <Step title="Check the Activity Log">
    **Reporting → Workflows → Activity Log** lists every processed event with the delivered payload, Meta's response and the HTTP status. `delivered` means Meta accepted it. See [Activity history](/conversion-tracking/activity-history).
  </Step>
  <Step title="Check Events Manager">
    Open your pixel's recent activity. Our server events arrive with `Hello Conversions` as the event source in `custom_data`.
  </Step>
</Steps>

`delivered` in the Activity Log but nothing in Events Manager means the events reached the right API with the wrong pixel — re-check the Pixel ID.

## When deliveries fail

After five consecutive failures to the same destination, deliveries pause for five minutes before a single request is retried, and the card flips to **Error** with Meta's message. The two failures worth knowing:

- **Token expired or permissions removed** — regenerate it in Events Manager, edit the destination, paste the new one and test again.
- **Pixel ID changed** — update the Pixel ID and re-test; existing connections keep pointing at the same destination record.

<Callout kind="tip">
  Saving a destination clears the cached copy the delivery worker holds, so a new pixel, token or currency applies to the next event. Deliveries already in flight finish with the old values.
</Callout>
