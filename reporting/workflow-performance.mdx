The [Activity Log](/conversion-tracking/activity-history) answers "did *this* conversion reach Meta?". **Reporting → Workflows → Overview** answers "is delivery healthy at all?"

Three rolling windows — **24h**, **7d** (default), **30d** — counting back from now, so "7d" at 2pm Thursday means since 2pm last Thursday. No custom range or comparison period. The screen refreshes every 60 seconds while **Auto** is lit.

## The four counters

Everything counts **runs**, not events: one event delivered to one connection. An event wired to three connections is three runs. Duplicates are dropped before logging.

| Counter | What it counts |
| --- | --- |
| **Total Events** | Every run in the window. Delivered + Failed + Filtered always sums to this. |
| **Delivered** | The destination's API accepted the payload — not the same as the platform attributing the conversion. |
| **Failed** | A request was rejected, or the destination was circuit-broken. Click to jump to the Activity Log filtered to failures. |
| **Filtered** | A filter rule rejected the event, or there was nothing usable to send. No request was made — a normal outcome, not an error. |

## Event Volume

Stacked bars of the same three outcomes: green delivered, grey filtered, red failed. One bar per hour on 24h, per day on 7d and 30d. Read it for shape — a step change to zero mid-window is the clearest break signal on the screen, and the bar tells you when to look.

## By Event Type

One row per source event type — Total, Delivered, Failed, and **Success** — with the raw event key next to the friendly name.

Success here is **(delivered + filtered) ÷ total**, because a filtered event is a rule doing its job. A row at 100% with a large Filtered share is heavily filtered, not broken.

This table catches *configuration* problems: a Purchase row far below expected volume, or an event type you wired last week that isn't listed, is upstream of delivery. See [Event Types](/conversion-tracking/event-types) and [Connections](/conversion-tracking/connections).

## By Destination

One card per destination platform, with total events, average delivery time, and a success percentage.

<Callout kind="warning">
  **By Destination and By Event Type calculate success differently.** By Destination is **delivered ÷ total**, counting filtered events in the total but not as successes; By Event Type counts filtered as success. A heavily-filtered project shows a low percentage here and 100% next to the same events above, with nothing failing. Judge failures by the red delivered/failed line, not the percentage.
</Callout>

The **ms avg** averages *delivered* calls only, so a destination whose runs all failed shows `0ms avg` — the absence of a successful call, not an instant one. Cards group by platform, not connection: two Meta pixels are added into one Meta CAPI card. For per-connection numbers, open the connection's runs from **Settings → Workflows → Connections**.

## Top Errors

Up to 20 distinct error messages, most frequent first, each with the platform's error title and detail, destination, source event type, error code, occurrence count, and how long ago it was last seen.

**Read Last seen first.** A large count last seen 20 hours ago is a fire already out — usually a since-reconnected token. A smaller count last seen "just now" is the live problem.

<Callout kind="note">
  Errors group by exact message text, and Meta stamps every response with a unique trace ID — so one Meta problem often appears as several entries with a count of 1 rather than one entry with a count of 12. Identical-looking rows are one problem.
</Callout>

The red badge totals occurrences of the errors *listed*, so with the list capped at 20 it can be lower than the Failed counter.

## Healthy, and not

Healthy is volume tracking the client's business rhythm with no cliff, Failed at zero or a handful against thousands, every configured destination and event type present, and the green "No errors in this period" state.

| Picture | Usual cause |
| --- | --- |
| A wall of failures on one destination, all the same error | Expired or revoked credentials. Reconnect under **Settings → Integrations → Destinations**. |
| Failures across event types, one destination | Destination-level: credentials, or a pixel/conversion action that no longer exists. |
| Failures on one event type across destinations | Connection-level: a payload or event-name problem on that wiring. |
| Volume drops to zero and stays | Nothing is arriving — check the source before the destinations. |
| Filtered climbs while Delivered falls | Nothing is failing; events stopped qualifying. A renamed pipeline stage is the usual culprit — see [Pipelines & Filters](/conversion-tracking/pipelines-filters). |
| Everything looks fine, but the client says conversions are missing | Delivery works; the gap is attribution, [match quality](/conversion-tracking/match-quality), or an event type never wired up. |

## Spotting a destination that has gone quiet

A destination that fails loudly is easy. One that simply stops costs a client money for weeks, because a screen full of green looks fine.

<Steps>
  <Step title="Compare the ranges">
    A destination present at 30d but missing or much smaller at 24h stopped in between; the volume chart shows roughly when.
  </Step>
  <Step title="Look for a card that's gone">
    By Destination only lists platforms with runs in the window, so a configured destination with no card sent nothing.
  </Step>
  <Step title="Work out which end went quiet">
    Total Events healthy but one destination vanished means that connection stopped matching arriving events — disabled, or filters that no longer match. Total Events down too means events stopped arriving; check the source.
  </Step>
  <Step title="Confirm in the Activity Log">
    Open the connection's runs from **Settings → Workflows → Connections** and read the most recent one.
  </Step>
</Steps>

## When the numbers look wrong

| Symptom | Cause |
| --- | --- |
| The whole screen is empty | No runs exist in the window. Events are only recorded once they reach an enabled connection — an event no connection listens for, an order not in a completed state, or an opportunity in an untargeted stage produces no run. Usually a configuration gap, not a delivery failure |
| One panel empty, the rest fine | Each section loads by its own query and a failed query returns empty rather than breaking the page. Hit **Refresh** first |
| Counters don't match the tables | Counters come from an hourly rollup; tables and chart read individual runs. At the edge of a long window counters can trail by up to an hour. A few events' difference is this; hundreds isn't |
| Filtered looks low on a pipeline-driven project | Pipeline-managed connections fan out across stages, and non-matching ones are deliberately not logged. Filtered reflects your own rules, not that internal partitioning |

This screen tells you *whether* something is wrong and *where*, never why. The Failed counter and **View all** both land you in the Activity Log pre-filtered.
